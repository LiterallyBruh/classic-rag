# ClassicLiteratureRAG — вопросно-ответная система по классической литературе

**Демо:** huggingface.co/spaces/ArtemResearch/ClassicLiteratureRAG ·
**Код:** github.com/LiterallyBruh/classic-rag

## Задача

Универсальные LLM галлюцинируют при вопросах по классической литературе:
уверенно выдумывают «цитаты» и перевирают адреса. Мы это измерили: у GigaChat
без RAG **0 из 27** закавыченных цитат нашлись в тексте дословно, номер главы
верен лишь в 2 случаях из 15 (см. «Результаты»). Для целевой аудитории —
школьников (сочинения, ЕГЭ), студентов и преподавателей — такой ответ
непригоден: его нечем проверить, а цена ошибки — оценка.

Существующие альтернативы не решают задачу: LLM-чаты дают непроверяемые
ответы; краткие содержания (Брифли и др.) не содержат цитат и адресов,
которые требуются в сочинении; полнотекстовый поиск (Ctrl+F) не понимает
перефразировок и алиасов («Родя», «князь»).

**ClassicLiteratureRAG** отвечает на вопросы по тексту произведений *только с опорой
на первоисточник*: каждое утверждение подкреплено дословной цитатой и
ссылкой на часть/главу, а если ответа в тексте нет — система честно
отказывается вместо правдоподобного вымысла.

## Данные

Корпус — четыре произведения в общественном достоянии: «Преступление и
наказание», «Идиот», «Бесы» (Ф. М. Достоевский) и «Фауст» И. В. Гёте строго
в переводе Н. Холодковского (современные переводы охраняются авторским
правом — выбор задокументирован). Итого ~650 тыс. слов, ~15 тыс. абзацев.

Пайплайн данных воспроизводим скриптами (тексты не хранятся в git):
скачивание с az.lib.ru → потоковая state-machine-очистка HTML-вёрстки →
структурная разметка: часть/глава для романов, сцены/реплики/говорящий для
драмы «Фауст». EDA-ноутбук обосновывает ключевые решения: распределения длин
абзацев → параметры чанкинга; частотный анализ имён → словарь алиасов
персонажей (87 строк, покрытие топ-имён проверено в ноутбуке).

Оценочный набор — 120 вопросов (по 30 на книгу) трёх типов: factual
(факты сюжета), quote (атрибуция цитат), interpretive (интерпретация).
Каждый вопрос имеет золотую локацию и gold-подстроку; валидность всех
120 проверяется программно против корпуса (`scripts/verify_eval.py`).

## Методы

Пайплайн: нормализация имён (алиасы расширяют запрос) → гибридный поиск —
BM25 (токенизация razdel) + dense multilingual-e5-base, слияние Reciprocal
Rank Fusion (не требует калибровки шкал) → cross-encoder
bge-reranker-v2-m3 (top-30 → top-6) → генерация GigaChat с обязательным
цитированием и фиксированным отказом. Индекс — файлы (chunks.jsonl +
embeddings.npy): на 10⁴ чанков полный перебор косинусов на numpy —
миллисекунды, векторная БД была бы лишней инфраструктурой.

Дизайн-решения приняты по экспериментам, а не «по умолчанию»:

- **Чанкинг**: сравнены три стратегии (окна ~180 слов с перекрытием,
  не пересекающие границ глав; по абзацам; по главам) на 120 вопросах —
  выбраны окна (таблица ниже).
- **Структурные вопросы**: класс отказов, найденный на живом демо
  («последняя фраза Мышкина» — similarity-поиск приносил главу 1: позиция
  в книге — не содержание). Такие запросы распознаются правилами и получают
  кандидатов срезом головы/хвоста книги; LLM дополнительно сообщается, что
  фрагменты — конец книги (это знание есть только у пайплайна).
- **LLM-слой** отделён адаптером: GigaChat с прозрачным кэшем OAuth-токена
  или любой OpenAI-совместимый эндпоинт — смена провайдера без правок кода;
  в тестах LLM и энкодеры подменяются фейками.

Инженерия: Python 3.11, зависимости через pyproject; 35 юнит-тестов без
сети; ruff + pytest в CI (GitHub Actions); Docker с CPU-сборкой torch
(экономия гигабайтов CUDA-библиотек); деплой на HF Spaces одним скриптом —
готовый индекс уходит в репозиторий Space через git-lfs, поэтому контейнер
стартует за секунды, а не пересобирает эмбеддинги 30+ минут.

Применение AI-инструментов: проект разработан в паре с Claude Code; каждый
шаг зафиксирован в `docs/ai_usage_log.md` (что делала LLM и как результат
проверялся человеком/программно), 13 дизайн-решений с аргументацией —
в `docs/decisions.md`.

## Результаты

**Retrieval** (span recall — в топ-k есть чанк с золотой подстрокой):

| Конфигурация | span@1 | span@5 | MRR |
|---|---|---|---|
| окна, гибрид BM25+e5 | 0.23 | 0.42 | 0.32 |
| **окна, гибрид + reranker** | **0.39** | **0.57** | **0.47** |
| абзацы, гибрид + reranker | 0.31 | 0.45 | 0.37 |
| главы, гибрид + reranker | 0.33 | 0.59 | 0.43 |

Реранкер — самый выгодный компонент: +70 % к span@1. Стратегия «по главам»
выигрывает только за счёт размера чанка и непригодна для генерации.

**Импакт** (та же модель GigaChat с RAG и без, 29 вопросов, автометрики:
дословность цитат по корпусу, леммная сверка с эталоном, номер главы):

| Метрика | LLM без RAG | ClassicLiteratureRAG |
|---|---|---|
| Цитаты дословно из текста | 0/27 | 8/9 |
| Ответ верен по сути | 10/29 | 11/29 |
| Верный номер главы | 2/15 | 12/15 |
| Честные отказы | — | 9/29 |

По существу системы сопоставимы, но ответ ClassicLiteratureRAG *проверяем*: цитаты
дословны, адрес верен, вместо вымысла — отказ. Именно это нужно ЦА.

**Продукт**: MVP задеплоен на HF Spaces (Docker); встроен сбор обратной
связи (оценка «помог / не помог» + комментарий → приватный HF-датасет,
переживающий рестарты);
цикл итерации по реальному фидбеку пройден (кейс структурных вопросов выше).

**Ограничения и развитие**: атрибуция реплик в диалогах (система честно
отказывается, если говорящий не назван во фрагменте); faithfulness-метрика
ответов LLM-судьёй; расширение корпуса — пайплайн данных к этому готов.
